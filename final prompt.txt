# AI GAME BUILDER v3.2  Финальная игра должна быть универсальной и запускаться на ЛЮБОЙ платформе (Яндекс Игры, VK, OK, CrazyGames, itch.io, Telegram Mini Apps, любой статический хостинг) БЕЗ серверной части (Backend).  КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать: - Серверный рендеринг (SSR, Server-Side Rendering). - Фреймворки и пресеты для серверов: Vercel, Nitro, Express, Next.js (App Router), TanStack Start (server parts), Nuxt. - Любые скрипты сборки, требующие запуска Node.js-сервера для отображения игры.  Разрешена ТОЛЬКО архитектура Single Page Application (SPA), которая после сборки (`npm run build`) выдает простую папку `dist`, содержащую `index.html`, `.js`, `.css` и папку `assets`. Эта папка должна корректно отображаться при простом двойном клике по `index.html` в браузере или при загрузке на любой игровой портал.  # PART 1. КОНТРАКТЫ  ## §1.0 ПРИНЦИП  15 контрактов. На скриншоте основного экрана в области игрового поля видны пиксели с hue в `hue_range ±15°`. Программно через PIL: обрезать HUD (верхние 15% и нижние 15% экрана), посчитать гистограмму hue, проверить ≥1% пикселей в диапазоне. Иначе `MISSING_IDENTITY_COLOR`.  **Error classes:** `MISSING_IDENTITY_COLOR_DATA`, `IDENTITY_COLOR_NOT_IN_PALETTE`, `IDENTITY_COLOR_NOT_IN_ROLES`, `MISSING_IDENTITY_COLOR`.  ## §1.12 READABILITY CONTRACT (§52A)  **Цель:** игрок отличает игровые объекты от поля и друг от друга без отладочной сетки.  **Классификация поля:** - `PHOTO_FIELD` — фото/детализированная текстура. - `PAINTED_FIELD` — рисованный фон с пятнами. - `GRAPHIC_FIELD` — плоская графика, pixel-art. - `SOLID_FIELD` — сплошная заливка, простой градиент. - `BOARD_FIELD` — поле из ячеек/карт/слотов.  **Классы объектов:** актор игрока, враги, collectible, препятствия, здания, фишки/гемы.  **Когда обязательно:** - PHOTO/PAINTED + объект близок к полю по тону. - BOARD_FIELD + фишка сливается с клеткой или соседом. - GRAPHIC_FIELD — только если после скриншота объект теряется. - SOLID_FIELD — NOT_APPLICABLE (кроме случая, когда объект того же цвета).  **Способы (минимально достаточный):** - Тонкая обводка по контуру (1 px pixel-art, 2-4 px HD). - Контрастная подложка (капсула, диск, плашка). - Тень по §1.12.1 (если одной тени достаточно). - Перекраска runtime-копии. - BOARD — обводка слота + selected/matched.  **Запрещено:** гигантский диск/«прожектор» под спрайтом. Тонкий контур — не он.  **Зачёт PASS только по скриншоту:** каждый обязательный класс отличим. Запрещены зачёты по «в промпте было isolated», «есть альфа», «только тень», «HUD контрастный», «mkTex-плейсхолдер с обводкой».  ## §1.12.1 SHADOW CONTRACT (§52)  Жанрозависимое правило тени. Проанализируй `ENGINE_SPEC` и `game_perspective`.  - **ЕСЛИ перспектива == `top-down` или `isometric`** И фон содержит сложные `depth_sprite` (параллакс) или детализированный `terrain_tile`: добавь под спрайтами игрока и ключевых врагов плоскую полупрозрачную тень для читаемости.    В Phaser 3: `this.add.ellipse(x, y + смещение_вниз, ширина_тела * 0.6, ширина_тела * 0.2, 0x000000, 0.25).setDepth(спрайт.depth - 0.1)`. Обновляй позицию в `update()`.    **ЗАПРЕЩЕНО:** чёрные круги `radius * 1.3`, тени, перекрывающие корпус, или тени для всех 100 врагов в пуле (только игрок и ближайшие).  - **ЕСЛИ перспектива == `side-view`:** тень не требуется, либо простая горизонтальная линия под ногами на платформе.  - **ЕСЛИ фон — простой программный градиент (`engine_backgrounds`) или сплошной цвет:** тень КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНА, используй только тонкую обводку по §1.12.  **ВАЖНО:** ассеты сгенерированы FLUX + BiRefNet — встроенные тени НЕ ГАРАНТИРОВАНЫ. Проверь визуально через Code Interpreter: если под объектом есть размытый тёмный эллипс — встроенная тень присутствует, дополнительную не добавлять. Если тени нет — применить §1.12.1 (top-down/isometric) или §1.12 (side-view, тонкая обводка). Приоритет — §1.12: тонкий контур всегда работает, мягкая тень — только для top_down/isometric.  ## §1.13 ORIENTATION CONTRACT (§52B)  **Источник:** `asset_spec.json` → `facing`.  **Область:** `template ∈ {humanoid, quadruped, flying, vehicle}` и `facing != null`. Для `crawling`/`amorphous` — не применяется. Для `icon`, `prop_*`, `tile_*`, `fluid`, `projectile`, `weapon_*` — не применяется.  **Определение фактического направления:** визуально через Code Interpreter.  **Правило коррекции:**  | declared | detected | action | |---|---|---| | right | вправо | ok | | right | влево | `setFlipX(true)` | | right | в камеру | `ORIENTATION_MISMATCH_RAKURS` | | left | влево | ok | | left | вправо | `setFlipX(true)` | | left | в камеру | `ORIENTATION_MISMATCH_RAKURS` | | front | в камеру | ok | | front | влево/вправо | `ORIENTATION_MISMATCH_RAKURS` |  **В коде:** ```javascript const FLIP_X_ASSETS = new Set([...]); if (FLIP_X_ASSETS.has(uid)) sprite.setFlipX(true); ```  **Артефакт `facing_audit.json`:** полная таблица (uid, reference_id, template, declared, detected, view, action, result).  **Повторная проверка:** после flip на рендере сборки игрок и 3-5 врагов смотрят по `facing`. Иначе `ORIENTATION_MISMATCH_FLIP`.  ## §1.14 WORLD SCALE CONTRACT (§53)  **Класс пространства по `space_model` (§1.2):** - `scrolling_tilemap` → Класс Б (скролл-мир). - `grid_tilemap` (arena/rooms) → Класс А. - `grid_abstract` / `track_lane` → Класс В. - `scene_flat` / `pinball_playfield` → Класс А (если сцена больше экрана — Класс Б).  **Класс А:** - `world = screen` или логические границы. - `zoom = Math.min(screenW / worldW, screenH / worldH)`, `startFollow` выключен. - Персонаж 7-15% высоты. - Фон: gradient или parallax.  **Класс Б:** - `world.width >> screen.width`. - `startFollow(player)`. - Фон: parallax с панорамированием. - Не растягивать короткий фон на длинный уровень.  **Класс В:** - Камера статична или integer scale. - Низкое внутреннее разрешение допустимо.  **Общие:** - Canvas ≥ 1280×720 для не-pixel-art. - `resolution: Math.min(2, window.devicePixelRatio || 1)`. - Приоритет логических границ над числами JSON. - Safe area. - Программные градиенты растягиваются без потери. Растровые — ≤15%. `parallax`/`background` — `setDisplaySize` допустим. `platform`/`wall` — `tileSprite`, не `setDisplaySize`.  ## §1.15 VISUAL SUFFICIENCY CONTRACT (§54)  **Инвентаризация слоёв:** для каждой роли (gradient, parallax, depth_sprite, terrain_tile, board_skin, prop_sprite, entities, vfx) — проверь наличие в сцене.  **Оценка по скриншоту:** 1. Фон не пустой холст (если `engine_backgrounds` есть). 2. Глубина: минимум 1 слой (если `depth_sprite` или `parallax` есть). 3. Поверхность: без дыр (если `terrain_tile` есть). 4. Атмосфера: есть `vfx_sprite` (если в данных). 5. Отделение объектов: каждый интерактивный отличим (§1.12). 6. Композиция: нет мёртвых регионов > 1/3 экрана. 7. Стиль: все слои в палитре темы. 8. Juice: `animation_class` у ключевых объектов. 9. Facing: акторы по `facing` (§1.13). 10. Decor density: по `decoration_density_target` (sparse 3-10, medium 15-25, dense 30-50, very_dense 50-80). 11. Light sources: по `light_layer_enabled` (yes: ≥2-3; optional: 0-3; no: пусто). 12. Tilemap: собран (если `tileset_enabled != "none"`). 13. Parallax: виден (если `parallax_layers` непуст). 14. Board skin: виден (если `board_skins` непуст). 15. Identity color: виден на основном экране (§1.11).  **Доработка (только визуальная):** реальные ассеты → процедурные средства (градиент, виньетка, геометрический декор). Запрещено: emoji, внешние изображения, заглушки, добавление геймплейных сущностей.  ---  **Конец PART 1.**  # PART 2. ПРОЦЕСС СБОРКИ  ## §2.0 ПОСЛЕДОВАТЕЛЬНОСТЬ  ``` 1. Juice.** - У ключевых интерактивных объектов есть `animation_class != "none"` и `interaction_class != "none"` (если интерактивны).  ## §3.8 ECONOMY QA  **Когда применимо:** если движок содержит экономику (ресурсы, стоимость, production, upgrades, rewards, unlock costs).  **Иначе:** `NOT_APPLICABLE`.  **Процедура:**  1. Открой игру на 1280×720. 2. Дойди до первого уровня с экономикой. 3. Выполни checks.  **Check 1. Начисление ресурсов.** - Выполни действие, дающее ресурс. Проверь: число в HUD увеличилось на ожидаемое значение.  **Check 2. Расход ресурсов.** - Купи объект/улучшение. Проверь: число уменьшилось на стоимость.  **Check 3. Стоимость.** - Проверь: стоимость отображается, совпадает с `progression.json`/`engine_spec.json`.  **Check 4. Production ticks.** - Если есть автоматическое производство: подожди 1-2 тика, проверь прирост.  **Check 5. Upgrades.** - Улучши объект. Проверь: числа изменились согласно формуле.  **Check 6. Rewards.** - Заверши уровень. Проверь: награда начислена.  **Check 7. Unlock costs.** - Проверь: unlock стоит ожидаемое значение, списывается корректно.  **Check 8. Balance constraints.** - При недостатке ресурса кнопка покупки disabled. Клик по disabled — ничего не происходит. - При достатке — покупка проходит. - Провал → `ECONOMY_BALANCE_BROKEN`.  **Check 9. NaN / Infinity.** - Проверь все числа в HUD после 10+ действий: нет `NaN`, нет `Infinity`. - Провал → `ECONOMY_NAN_INFINITY`.  **Check 10. Отрицательный баланс.** - Проверь: ресурс не уходит в минус при корректных действиях. - Провал → `ECONOMY_NEGATIVE_BALANCE`.  **Error classes:** `ECONOMY_BALANCE_BROKEN`, `ECONOMY_NAN_INFINITY`, `ECONOMY_NEGATIVE_BALANCE`.  ## §3.9 TIMERS QA  **Когда применимо:** если движок содержит таймеры (production ticks, cooldown, offline progress, события по времени, wave timers).  **Иначе:** `NOT_APPLICABLE`.  **Процедура:**  1. Открой игру на 1280×720. 2. Дойди до уровня с таймерами. 3. Выполни checks.  **Check 1. Запуск.** - Таймер запускается при входе в состояние. Проверь: счётчик уменьшается/увеличивается.  **Check 2. Остановка.** - Таймер останавливается при выходе из состояния. Проверь: счётчик стоит.  **Check 3. Повторный запуск.** - Выйди и вернись. Проверь: таймер запускается заново без двойного начисления.  **Check 4. Переход между уровнями.** - Перейди на следующий уровень. Проверь: таймер предыдущего не продолжает работать.  **Check 5. Reload.** - Перезагрузи страницу. Проверь: таймер восстанавливается корректно.  **Check 6. Восстановление после reload.** - Если есть offline progress: проверь, что за время отсутствия начислено ожидаемое, не больше. - Провал → `TIMER_OFFLINE_BROKEN`.  **Check 7. Двойное начисление.** - Проверь: за один тик начисляется один раз, не два. - Провал → `TIMER_DOUBLE_ACCRUAL`.  **Check 8. Runaway timer.** - Проверь: нет `setInterval` без `clearInterval`. Нет `requestAnimationFrame` без остановки. - Провал → `RUNAWAY_TIMER`.  **Error classes:** `TIMER_OFFLINE_BROKEN`, `TIMER_DOUBLE_ACCRUAL`, `RUNAWAY_TIMER`.  ## §3.10 PROGRESSION REACHABILITY QA  **Процедура:**  1. Прочитай `progression.json`: `macro_levels[]`, `unlock_conditions`, `progression_goals`. 2. Для каждого unlock/требования выполни алгоритм.  **Алгоритм:** ``` REQUIREMENT ↓ CAN PLAYER OBTAIN REQUIRED VALUE? ↓ CAN PLAYER PERFORM REQUIRED ACTION? ↓ DOES ACTION UNLOCK TARGET? ```  **Check 1. Достижимость значений.** - Каждое требуемое значение (ресурс, счёт, уровень) достижимо из текущего состояния. - Провал → `PROGRESSION_UNREACHABLE`.  **Check 2. Достижимость действий.** - Каждое требуемое действие выполнимо (кнопка доступна, объект на карте). - Провал → `PROGRESSION_ACTION_UNAVAILABLE`.  **Check 3. Разблокировка цели.** - Действие фактически разблокирует целевой контент. - Провал → `PROGRESSION_UNLOCK_BROKEN`.  **Check 4. Циклические зависимости.** - A требует B, B требует C, C требует A — цикла быть не должно, если движок не предусматривает механизма разрешения. - Провал → `PROGRESSION_CYCLE`.  **Error classes:** `PROGRESSION_UNREACHABLE`, `PROGRESSION_ACTION_UNAVAILABLE`, `PROGRESSION_UNLOCK_BROKEN`, `PROGRESSION_CYCLE`.  ## §3.11 RESET QA  **Когда применимо:** если в игре есть Reset/New Game.  **Иначе:** `NOT_APPLICABLE`.  **Процедура:**  1. Прогрессируй в игре (построй объект, купи upgrade, unlock контент). 2. Сохрани. 3. Нажми Reset/New Game. 4. Проверь:  **Check 1. Ресурсы сброшены** к начальному значению. **Check 2. Построенные объекты сброшены.** **Check 3. Upgrades сброшены.** **Check 4. Unlocks сброшены.** **Check 5. Progression сброшена.** **Check 6. UI сброшен** (нет старых панелей). **Check 7. Старое сохранение не возвращается** (reload не восстанавливает старые данные).  **Провал → `RESET_INCOMPLETE`.**  **Error classes:** `RESET_INCOMPLETE`.  ## §3.12 CANVAS QA  **Процедура:**  1. Открой игру на 1280×720. 2. Выполни checks.  **Check 1. Resize.** - Измени размер окна. Проверь: canvas перерисовывается, нет артефактов.  **Check 2. DevicePixelRatio.** - Проверь `window.devicePixelRatio` в консоли. Canvas внутренний буфер учитывает DPR (`resolution: min(2, dpr)`).  **Check 3. Отсутствие размытия.** - На скриншоте нет «мыла» на статичных элементах, текст читаем.  **Check 4. Корректное масштабирование.** - Объекты не растянуты, пропорции сохранены.  **Check 5. Соответствие координат мыши/тача.** - Клик по кнопке в canvas → handler срабатывает по правильным координатам. - Провал → `CANVAS_COORDINATES_MISMATCH`.  **Check 6. Hitboxes.** - Клик по краю кнопки → срабатывает. Клик мимо — не срабатывает. - Провал → `CANVAS_HITBOX_BROKEN`.  **Check 7. Рассинхронизация DOM и Canvas.** - Если HUD в DOM — при resize canvas HUD остаётся на месте. - Провал → `CANVAS_DOM_DESYNC`.  **Check 8. Объекты за пределами области.** - Игровые объекты не выходят за границы canvas.  **Check 9. Корректная перерисовка.** - После изменения состояния canvas обновляется без артефактов.  **Error classes:** `CANVAS_COORDINATES_MISMATCH`, `CANVAS_HITBOX_BROKEN`, `CANVAS_DOM_DESYNC`, `CANVAS_RESOLUTION_MISMATCH`.  ## §3.13 STATIC CODE QA  **Процедура:**  1. Прочитай исходники `dist/assets/*.js`, `dist/index.html`. 2. Выполни checks.  **Check 1. HTML.** - Все теги закрыты. - `<script>`, `<link>` подключены. - Пути корректны.  **Check 2. JavaScript.** - Нет syntax errors (`node --check`). - Нет `undefined variables` / `undefined functions`. - Нет конфликтующих переменных. - Нет незакрытых блоков. - Нет неправильных ссылок на `GAME_DATA`.  **Check 3. GAME_DATA.** - Обязательные поля на месте. - ID консистентны. - Нет ссылок на несуществующие объекты. - `world` соответствует логическим границам (для одноэкранных жанров).  **Check 4. ASSETS.** - Все пути существуют. - Расширения корректные. - Размеры файлов соответствуют ожидаемым. - `facing` в `asset_spec` соответствует `facing_audit`.  **Check 5. ENGINE.** - Игровой цикл инициализируется. - Save/load работает. - UI инициализируется. - Состояния и переходы определены.  **Провал любого check → `STATIC_CODE_FAILED`.**  **Error classes:** `STATIC_CODE_FAILED`, `STATIC_HTML_FAILED`, `STATIC_JS_FAILED`, `STATIC_DATA_FAILED`.  ## §3.14 PRINCIPLE: NO PROOF BY EXISTENCE  **Фундаментальный принцип QA.**  Нельзя считать задачу выполненной после генерации кода. Обязательная последовательность: ``` CODE → BUILD → RUN → STATIC QA → FUNCTIONAL QA → PROGRESSION QA → SAVE/LOAD QA → VISUAL QA → UX/CONTENT QA → PERFORMANCE QA → MOBILE TOUCH QA → FULL PLAYTHROUGH → FIX → REBUILD → RETEST → FINAL QA ```  **Запрещено считать доказательством работоспособности:**  - Синтаксическую корректность (не доказывает, что код работает). - Наличие функции (не доказывает, что она работает). - Наличие ассета (не доказывает, что он отображается). - Наличие `progression.json` (не доказывает, что progression работает). - Наличие CSS (не доказывает визуальную готовность). - `Scale.FIT` (не доказывает резкость). - Наличие ассета и альфа-канала (не доказывает читаемость на игровом поле). - Тень §1.12.1 (не доказывает §1.12 Readability). - Наличие поля `facing` в манифесте (не доказывает, что PNG сгенерился в правильном направлении — надо проверить визуально). - Наличие полного tile-ID в legend (не доказывает, что текстура загрузилась и отрендерилась). - Наличие `micro.parallax_layers` (не доказывает, что слои видны и alpha корректна).  **Каждая проверка — фактическая, через Code Interpreter / headless browser / скриншот. Не «должно работать», а «работает».**  ## §3.15 BLOCKING STATES QA  **Цель:** исключить сценарии, при которых игра формально запускается, но фактически блокирует ввод или зависает.  **Процедура:**  **Шаг 1. Карта критических состояний.**  Для каждого состояния (MENU, PLAYING, PAUSED, GAME_OVER, VICTORY, LOADING, TRANSITION, MODAL) зафиксируй: - Какой DOM/Canvas-слой активен. - Какие элементы принимают ввод. - Какой код отвечает за выход из состояния. - Есть ли в этом коде `while`, синхронный `fetch`, `await` без таймаута, рекурсия.  **Шаг 2. Проверка оверлеев.**  Для каждого DOM-слоя поверх canvas: - `pointer-events: none` для декоративных слоёв. - `pointer-events: auto` ТОЛЬКО на кликабельных элементах. - `z-index` корректный. - Нет `width: 100vw; height: 100vh` контейнеров с `pointer-events: auto` без дочерних кликабельных элементов — это blanket blocker.  Провал → `BLANKET_BLOCKER`.  **Шаг 3. Проверка зависаний.**  Для каждого состояния: - Открой DevTools → Performance → Record. - Войди в состояние, ничего не делай 10 секунд. - Останови запись. - Проверь: нет длинных task (>50ms подряд), нет петель в `update()`, нет утечки `setInterval`/`setTimeout`. - CPU не должен расти.  Провал → `CPU_LEAK_IN_IDLE`, `MENU_FREEZE`.  **Шаг 4. Проверка выхода.**  Для каждого состояния: - `Esc` работает (кроме состояний, где Esc запрещён геймплеем — перечислить явно). - Кнопка «В меню» / «Закрыть» работает. - Автопереход по таймеру имеет разумный таймаут (не > 5 сек без UI-индикатора). - Состояние не накладывается на другое (нельзя открыть паузу на экране смерти, если это не предусмотрено).  Провал → `BLOCKING_STATE_DEFECT`.  **Error classes:** `BLANKET_BLOCKER`, `CPU_LEAK_IN_IDLE`, `MENU_FREEZE`, `BLOCKING_STATE_DEFECT`.  ## §3.16 REPAIR PROTOCOL  При провале QA:  ``` IDENTIFY (какая категория, какая проверка, какой error class) ↓ ROOT CAUSE (upstream данные, код сборки, код движка) ↓ REPAIR (минимальное исправление) ↓ REBUILD ↓ RETEST (соответствующая QA + связанные) ↓ FINAL QA ```  **Связанные повторные тесты:**  | Исправлено | Повторить | |---|---| | tile_map | RENDER QA (surface), PHYSICS QA, playthrough | | surface_layout | RENDER QA (surface), PHYSICS QA, region unity, playthrough | | parallax | RENDER QA (bg_far/mid/near), visual QA фона, playthrough | | board_skin | RENDER QA (board), visual QA поля, playthrough | | light_sources | RENDER QA (lights), visual QA, playthrough | | identity_color | DATA QA (identity), RENDER QA (identity visible), visual QA, playthrough | | facing | facing_audit, RENDER QA (facing), playthrough | | motion_animations | ANIMATION QA, visual QA движущихся объектов, playthrough | | audio | DATA QA (audio), UX QA (mute), playthrough | | first_screen | STATE QA (splash→title→intro→tutorial), visual QA меню, playthrough | | lore | STATE QA (lore layer), visual QA интро, playthrough | | postgame | STATE QA (postgame), playthrough после финала | | signature_mechanics | STATE QA (signature), playthrough соответствующего макро | | pause/Esc | STATE QA (PAUSED), PHYSICS QA, playthrough | | pointer_events | UX QA (pointer), visual QA меню, playthrough |  ## §3.17 STATUS CLASSIFICATION  **Статусы:**  - `BUILD_FAILED` — проект невозможно собрать. - `QA_FAILED` — сборка создана, но обнаружены критические ошибки. - `REPAIR_REQUIRED` — обнаружена ошибка, которую необходимо исправить. - `RETEST_REQUIRED` — исправление внесено, нужно повторить соответствующий тест. - `READY` — все критические проверки пройдены. - `REJECTED` — невозможно получить рабочий результат после допустимых попыток исправления.  **Правило:** `READY` запрещён, если хотя бы одна критическая проверка провалена или не выполнена фактически.  ## §3.18 ФИНАЛЬНЫЙ GATE  `READY` только если пройдены все применимые категории:  - Если значение НЕ начинается с `tile_` — legacy-формат. Fallback:    - Найди в `macro.entity_ids` все сущности, чей `id` начинается с `tile_<тип>_`.    - Если найдена ровно одна — используй её.    - Если найдено ноль — используй `mkTex`-плейсхолдер (для OPTIONAL) или `REPAIR_REQUIRED` (для CRITICAL).    - Если найдено больше одной — `REPAIR_REQUIRED`, не собирай tile_map.  **Проверка единства региона:** все ID одной микро (после резолва) должны иметь одинаковый `register_id`. Click → `sfx.mute(!sfx.muted)` + переключение иконки.  ## §4.8 REFERENCE: WORLD SCALE AND CAMERA (§53)  **Класс пространства по `space_model` (§1.2):**  - `scrolling_tilemap` → **Класс Б (скролл-мир).** - `grid_tilemap` (arena) → **Класс А (одноэкранная арена).** - `grid_tilemap` (rooms) → **Класс А (модульные комнаты).** - `grid_abstract` / `track_lane` → **Класс В (UI-поле).** - `scene_flat` / `pinball_playfield` → **Класс А (одноэкранная сцена).** Если сцена больше экрана — Класс Б.  ### Класс А (арена/комнаты/сцена)  - `world = screen` или логические границы арены/сетки. - Камера: `zoom = Math.min(screenW / worldW, screenH / worldH)`, `startFollow` выключен или мёртвая зона = мир. - Персонаж 7-15% высоты экрана. - Фон: gradient или parallax `setDisplaySize`. - Растяжение растровых текстур ≤ 15%.  ### Класс Б (скролл-мир)  - `world.width >> screen.width` (например, 3000×768). - Камера: `startFollow(player)`. - Фон: parallax с панорамированием (`sprite.x = camera.scrollX * (1 - pf)`). - Не растягивать короткий фон на длинный уровень.  ### Класс В (UI-поле)  - Камера статична или integer scale. - Низкое внутреннее разрешение буфера допустимо (pixel-art).  ### Общие правила  1. **Приоритет реальных пикселей:** числа `world`/`screen` в JSON не важнее реального разрешения файла ассета или логических границ. Если логические границы 1024×768, а в JSON мир 1500×1100 для Класса А — исправь JSON или код в пользу 1024×768. 2. **Инициализация Canvas:** внутреннее разрешение Canvas ≥ 1280×720 для не-pixel-art. `resolution: Math.min(2, window.devicePixelRatio || 1)`. Запрещено создавать canvas 800×600 и полагаться на CSS-растягивание. 3. **Safe Area:** HUD и кнопки учитывают `env(safe-area-inset-*)`. 4. **Программные градиенты** (`engine_backgrounds`) растягиваются без потери качества. Растровые текстуры (`terrain_tile`, `board_skin`, `depth_sprite`, tile-ассеты) — ≤ 15%. `parallax_layer` / `background_layer` — `setDisplaySize` допустим (это цельные фоновые сцены, силуэты). `platform_sprite` / `wall_sprite` — `tileSprite`, не `setDisplaySize` (это даст мыло). 5. **Проверка на скриншоте:** на любом целевом разрешении нет артефактов растяжения, чёрных полос там, где их не должно быть, обрезанного критического интерфейса.  ## §4.9 REFERENCE: VISUAL SUFFICIENCY (§54)  ### Инвентаризация слоёв  Прочитай `asset_manifest_slice` и определи, какие роли присутствуют в данных:  - `engine_backgrounds` → программный градиент дальнего фона. - `parallax_layer` / `background_layer` → параллакс-слои глубины. - `depth_sprite` → слой глубины / среднего плана. - `terrain_tile` → поверхность / поле / ячейки / слоты. - `board_skin` → цельная поверхность поля для `grid_abstract`. - `prop_sprite` → декор переднего плана. - `player_sprite` / `enemy_sprite` / `collectible_sprite` / `interactive_sprite` / `npc_sprite` / `hazard_sprite` → интерактивные объекты и акторы. - `vfx_sprite` → атмосфера и эффекты.  Для каждой роли, присутствующей в данных, определи, представлена ли она в итоговой сцене. Роль есть в данных, но отсутствует в сцене = визуальный недостаток.  ### Оценка по скриншоту (19 пунктов)  1. **Фон:** поле за интерактивными объектами не является пустым холстом или голой заливкой, если данные содержат `engine_backgrounds` или тема не требует пустоты (SOLID_FIELD). 2. **Глубина:** если данные содержат `depth_sprite` или `parallax_layer` — в сцене присутствует минимум один слой глубины; сцена не выглядит плоской. 3. **Поверхность:** если данные содержат `terrain_tile` — поле/поверхность/ячейки собраны без дыр, швов, пропусков. 4. **Атмосфера:** если данные содержат `vfx_sprite` или тема требует свечения/дымки/света — в сцене присутствуют атмосферные акценты, не ухудшающие читаемость. 5. **Отделение объектов:** каждый интерактивный объект (актор, фишка, карта, слот, ячейка, полевой элемент) визуально отделён от поля по §1.12. 6. **Композиция:** нет мёртвых пустых регионов > 1/3 экрана без декора/градиента/виньетки; соблюдена иерархия слоёв. 7. **Стилевое единство:** все слои делят палитру и свет темы; нет слоя, выглядящего чужеродно. 8. **Juice:** интерактивные объекты (игрок, цели, кнопки, collectible) имеют «дыхание» (`anim-idle`) или реагируют на наведение/клик (`anim-hover`/`anim-interact`). Массовые фоновые объекты и декорации (`depth_sprite`) остаются статичными. 9. **Ориентация акторов:** игрок, враги, NPC, транспорт на скриншоте основного экрана смотрят по `facing` из `asset_spec.json` (§1.13). 10. **Плотность декораций:** `dense` → 30-50, `very_dense` → 50-80. 11. **Световые источники:** `yes` → ≥ 2-3 источника. 12. **Тайлсет:** при `tileset_enabled = "full"`/`"partial"` сцена собрана из тайлов, не голый градиент. Тайлы одной микро единообразны (один регион). 13. **Формат legend:** значения — полные ID (или легаси-типы). На скриншоте нет «заплаток» — текстур, выбивающихся по материалу. 14. **Лор-слой:** на экране запуска видны `theme_name` и `onboarding_text`. Перед первым уровнем — интро (с «Пропустить»). Между макро 2+ — плашка с `narrative_summary`. 15. **Звуковая иконка:** в правом верхнем углу главного меню видна кнопка mute. 16. **Кнопка постгейма в меню:** после прохождения финала появилась кнопка постгейма. 17. **Анимации движения:** персонаж не «едет как слайд» — есть bob при беге. Прыжок имеет squash и stretch. Приземление даёт отскок. Враги при смерти исчезают с анимацией. Collectible подпрыгивают. Листья качаются. Вода мерцает. Параллакс дрейфует. 18. **Parallax-слои:** если `parallax_layers` непуст — видны характерные силуэты/формы фона поверх градиента. 19. **Board skin:** если `board_skins` непуст — видна цельная поверхность поля (не сетка тайлов).  ### Доработка (только визуальная)  1. Реальные ассеты из `assets/` по роли: `parallax_layer` → параллакс-слои, `depth_sprite` → слой глубины, `prop_sprite` → декор пустых регионов, `vfx_sprite` → атмосфера. 2.
